# 多 Agent 协作

多 Agent 系统把一个复杂任务拆给多个具有不同职责的 Agent。它不是“多开几个聊天窗口”，而是要解决角色边界、交接协议、共享状态、冲突处理和最终验收。

## 什么时候值得使用

适合任务可以自然分工、需要并行探索或需要独立审查的场景，例如研究—写作—审校。步骤固定且单个 Agent 已能稳定完成时，不要为了追求复杂度引入多 Agent。

## 三种基本拓扑

| 拓扑 | 特点 | 适合场景 |
| --- | --- | --- |
| 顺序流水线 | 前一个输出交给下一个 | 写作、转换、审批 |
| 并行汇总 | 多个 Agent 独立处理后汇总 | 多来源研究、候选方案比较 |
| 管理者—专家 | 管理者拆解和分派，专家执行 | 路径不确定、需要动态分工 |

## 角色设计

每个 Agent 应有单一职责、输入输出 schema、可用工具、预算和完成条件。角色描述不要只写“你是专家”，要写清楚：

- 可以读取和修改什么；
- 必须返回哪些字段和证据；
- 失败时如何报告；
- 何时把任务交回管理者或请求人工介入。

## 交接协议

```json
{
  "task_id": "task-123",
  "status": "completed",
  "result": "摘要或产物引用",
  "evidence": ["doc-1#section-2"],
  "open_questions": [],
  "next_action": "review"
}
```

共享状态应保存事件和版本，而不是让所有 Agent 共享一段无限增长的聊天记录。交接时传递最小必要上下文、来源和未决问题。

## 冲突与失败

- 两个 Agent 结论冲突：保留证据，让审查 Agent 或人工决定，不用随机投票掩盖差异。
- 某个 Agent 超时：重试要有幂等键和次数上限，必要时降级为人工处理。
- 管理者循环分派：设置最大深度、总步数和费用预算。
- 专家返回未经验证的事实：标记置信度和来源，不能直接发布。

## 框架选择原则

框架不是架构本身。选择时优先比较状态持久化、重试/暂停、工具权限、追踪、测试和部署方式，而不是只看示例代码或社区热度。固定 DAG 可用工作流；需要状态和分支时使用图编排；简单协作可先用应用代码实现。

## 评估

除了最终任务成功率，还要测：分派准确率、交接完整率、重复工作比例、平均并行度、冲突解决率、单任务成本、延迟、人工接管率和安全拦截率。评估集应包含缺失信息、互相矛盾的来源、工具失败和恶意输入。
