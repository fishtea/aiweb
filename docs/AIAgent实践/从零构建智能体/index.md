## 一、什么是智能体

### 1.1 经典定义

> **智能体（Agent）**：任何能够通过**传感器**感知所处环境，并自主地通过**执行器**采取行动，以达成特定目标的实体。

五大核心要素：

| 要素 | 含义 |
|------|------|
| **环境（Environment）** | Agent 所处的世界（物理或数字） |
| **传感器（Sensors）** | 感知环境输入的通道 |
| **执行器（Actuators）** | 对环境施加行动的通道 |
| **行动（Action）** | 为达成目标执行的操作 |
| **自主性（Autonomy）** | 不依赖外部指令、自主决策的能力 |

### 1.2 传统智能体的五种类型

| 类型 | 决策依据 | 局限 |
|------|---------|------|
| **反射智能体** | 直接依据当前感知做反应 | 无记忆，无法处理复杂任务 |
| **基于模型的反射智能体** | 维护环境内部模型，结合历史决策 | 无法主动规划目标 |
| **基于目标的智能体** | 面向目标选择行动序列 | 目标单一，缺乏权衡 |
| **基于效用的智能体** | 用效用函数量化「好坏」再决策 | 效用函数难设计 |
| **学习型智能体** | 从经验中持续改进 | 依赖训练数据与反馈 |

### 1.3 LLM 驱动的新范式

LLM 智能体通过海量数据预训练获得**隐式世界模型**与**涌现能力**，能直接处理高层级、模糊的自然语言指令，而无需传统符号系统显式建模。这是 Agent 从「专用」走向「通用」的关键转折。

### 1.4 运行机制：Agent Loop

```
感知（Perception） → 思考（Thought） → 行动（Action） → 观察（Observation） → 回到感知
                            │
                            ├── 规划（Planning）
                            └── 工具选择（Tool Selection）
```

交互遵循 **Thought-Action-Observation 协议**：Agent 输出结构化的「思考 + 行动」，环境返回「观察」作为下一轮输入。

### 1.5 Workflow 与 Agent 的区别

| | Workflow（工作流） | Agent（智能体） |
|---|---|---|
| **执行方式** | 按部就班执行预设指令 | 赋予自由度，自主达成目标 |
| **关键能力** | 确定性、可预测 | 自主性、目标导向、动态行动 |
| **适用场景** | 步骤固定、可预见 | 路径不确定、需要灵活决策 |

> 经验法则：能用工作流解决的不要用 Agent——自主性的代价是更高的不确定性。

## 二、构建智能体所需的 LLM 基础

### 2.1 语言模型与 Transformer

- **语言模型（LM）**：计算词序列出现概率，是 Agent 理解指令、生成回应的基础。
- **N-gram → 词嵌入 → RNN → LSTM**：从马尔可夫假设出发逐步演进，解决泛化与长期依赖问题。
- **Transformer**：完全抛弃循环结构，依赖**自注意力（Self-Attention）**实现并行计算。通过 Query/Key/Value 计算注意力权重，配合多头注意力、残差连接、层归一化与位置编码。
- **Decoder-Only 架构**（如 GPT）：只保留解码器，以**自回归**方式「预测下一个词」，用掩码自注意力防止「偷看」未来。

### 2.2 与大语言模型交互

| 技术 | 要点 |
|------|------|
| **提示工程（Prompt Engineering）** | 通过设计精准提示引导输出 |
| **Temperature / Top-k / Top-p** | 控制采样随机性与确定性 |
| **Zero-shot / One-shot / Few-shot** | 是否给示例、给多少示例 |
| **思维链（CoT）** | 引导模型「一步一步思考」，提升复杂推理 |
| **指令调优 / 角色扮演 / 上下文示例** | 让模型遵循指令、扮演角色、参考范例 |

**分词（Tokenization）**：文本切分为模型能处理的最小单元。主流**子词分词**（如 BPE 字节对编码）兼顾词表大小与语义表达。

### 2.3 模型选型与缩放法则

- **选型考量**：性能、成本、速度、上下文窗口、部署方式、生态工具链、可微调性、安全伦理。
- **闭源 vs 开源**：GPT/Gemini/Claude 代表前沿；Llama/Qwen/ChatGLM 提供灵活与自主。
- **缩放法则（Scaling Laws）**：性能与参数量、数据量、算力呈可预测幂律关系；**Chinchilla 定律**强调参数与数据的**最优配比**；**能力涌现**指规模过阈值后出现全新能力。

### 2.4 模型幻觉与缓解

幻觉（Hallucination）指模型生成与事实、输入或上下文矛盾的内容，分**事实性幻觉**与**忠实性幻觉**。缓解手段：

1. **数据层面**：高质量数据清洗、引入事实性知识、RLHF。
2. **推理与生成层面**：
   - **RAG（检索增强生成）**：生成前从外部知识库检索相关信息，引导基于事实的回答。
   - 多步推理与验证、引入外部工具。

## 三、智能体三大经典范式

### 3.1 ReAct（推理 + 行动）

将**推理（Reasoning）**与**行动（Acting）**显式结合，形成「思考 → 行动 → 观察」循环：

```
Thought（思考）→ Action（行动/工具调用）→ Observation（观察）→ 回到 Thought
```

- **特点**：高可解释性、动态规划、自我纠错、工具协同。
- **局限**：强依赖 LLM 能力、执行效率偏低、提示词脆弱、可能陷入局部最优。
- **适用**：探索性、需要外部工具输入的任务。

### 3.2 Plan-and-Solve（先规划后执行）

任务分为「先规划（Plan）后执行（Solve）」两个阶段：先生成完整计划，再严格按计划逐步执行。

- **特点**：结构清晰、执行稳定。
- **局限**：对任务可分解性要求高。
- **适用**：结构性强、可清晰分解的复杂任务（如逻辑路径确定的推理）。

### 3.3 Reflection（自我反思与迭代）

引入「事后自我校正循环」，形成「执行 → 反思 → 优化」三步闭环：审视工作、发现不足、迭代优化。

- **特点**：提供内部纠错回路，持续优化质量，构建临时「短期记忆」。
- **局限**：增加推理轮次与成本，对实时性不友好。
- **适用**：对结果质量、准确性和可靠性要求极高、且对实时性要求宽松的场景。

### 3.4 范式选型策略

| 范式 | 核心循环 | 一句话适用场景 |
|------|---------|--------------|
| **ReAct** | 思考 → 行动 → 观察 | 探索性强、需要外部工具 |
| **Plan-and-Solve** | 规划 → 执行 | 逻辑路径确定、内部推理密集 |
| **Reflection** | 执行 → 反思 → 优化 | 质量要求极高、可容忍多轮 |

## 四、记忆与检索（RAG）

### 4.1 为什么智能体需要记忆

- **无状态（Stateless）**：LLM 每次请求相互独立，无法记住历史对话。
- **知识时效性**：模型知识存在训练截止点，无法获取最新信息。
- 因此需要**记忆系统** + **RAG** 补足。

### 4.2 记忆系统：四种记忆类型

参考认知科学（感觉记忆 / 工作记忆 / 长期记忆），Agent 记忆分四类：

| 记忆类型 | 存储方式 | 用途 |
|---------|---------|------|
| **工作记忆（Working）** | 纯内存，词法检索 | 当前对话上下文，生命周期短 |
| **情景记忆（Episodic）** | SQLite + 向量库混合 | 具体交互事件，时间序列检索 |
| **语义记忆（Semantic）** | 图数据库 + 向量库 | 抽象知识、概念与规则，知识体系 |
| **感知记忆（Perceptual）** | 多模态分离存储 | 图像、音频等，跨模态检索 |

**记忆工作流**：编码 → 存储 → 检索 → 整合（短期转长期）→ 遗忘（重要性/时间/容量策略）。

### 4.3 RAG 系统

**RAG（检索增强生成）**：结合信息检索与文本生成，从外部知识库检索相关信息作为上下文，生成更准确可靠的回答。

- **数据准备**：数据提取 → 文本分割（智能分块）→ 向量化 → 存储。
- **应用阶段**：提问 → 检索 → 注入 Prompt → 生成答案。
- **发展历程**：朴素 RAG（关键词）→ 高级 RAG（稠密嵌入语义检索）→ 模块化 RAG（混合检索）。

**高级检索策略**：
- **多查询扩展（MQE）**：生成语义等价的多样化查询，提高召回率。
- **假设文档嵌入（HyDE）**：「用答案找答案」——让 LLM 生成假设性答案段落，再用其检索真实文档。

## 五、智能体通信协议

### 5.1 为什么需要通信协议

- **工具集成困境**：每个外部服务都要写专门的 Tool 类，工作量大且不兼容。
- **能力扩展瓶颈**：智能体受限于预定义工具集，无法动态发现新服务。
- **协作缺失**：复杂任务需多智能体协作，传统方式只能手动编排。

### 5.2 三大协议设计理念

| 协议 | 解决什么 | 设计哲学 |
|------|---------|---------|
| **MCP（Model Context Protocol）** | 智能体与外部工具/资源的通信 | 上下文共享 |
| **A2A（Agent-to-Agent Protocol）** | 智能体之间的点对点通信 | 对等通信 |
| **ANP（Agent Network Protocol）** | 大规模智能体网络基础设施 | 去中心化服务发现 |

### 5.3 MCP 协议要点

- **三层架构**：Host（用户界面）→ Client（协议通信）→ Server（功能实现）。
- **核心能力**：Tools（执行操作）、Resources（提供数据）、Prompts（提供模板）。
- **传输方式**：内存、Stdio（本地开发）、HTTP（生产远程）、SSE（流式）、StreamableHTTP（双向流式）。
- **与 Function Calling 的区别**：Function Calling 是模型能力（「如何打电话」），MCP 是基础设施协议（「电话通信标准」）。

## 六、智能体性能评估

### 6.1 为什么 Agent 评估更难

Agent 执行路径**非确定性**——同一输入可能触发完全不同的工具调用序列，传统 API 指标（延迟、错误率）不足以衡量。

### 6.2 需要关注的评估维度

| 维度 | 说明 |
|------|------|
| **过程指标** | 工具选择准确率、参数正确率、步数效率、循环检测、失败恢复率 |
| **结果指标** | 任务完成率、答案正确性、忠实度（是否基于工具真实结果）、引用准确率、安全性 |
| **可观测性** | 记录思考轨迹、工具调用、参数、结果与耗时，用于调试与复盘 |

> 评估工具链：LangSmith、LangFuse 等提供从开发追踪到生产监控的完整方案。
