# 长任务与长记忆架构

本文把“Agent 能不能持续工作”拆成可实现的工程问题：运行时如何选、任务状态如何保存、上下文如何压缩、记忆如何检索、失败如何恢复，以及结果如何生成文档并发布。

> 资料基线：2026-10-08。官方能力和 API 会变化，涉及具体模型、额度或版本时，应以供应商最新文档为准。

## 适合读者

- 需要构建研究、编程、内容生产或运营自动化 Agent 的开发者
- 需要把一次性对话升级为可暂停、可恢复、可审计任务的产品和架构人员
- 维护本知识库，希望把采集、整理、构建和发布做成可靠流水线的贡献者

## 先选运行时，再设计状态

当前 Agent 系统可以按“谁控制循环、谁保存状态”选择入口：

| 入口 | 适合场景 | 状态责任 | 主要取舍 |
| --- | --- | --- | --- |
| Agents API | 长时间运行、希望托管执行和进度保存的任务 | 平台保存会话配置、回合和项目 | 接入快，但运行环境和生命周期受平台约束 |
| Agents SDK | 应用内自定义工具、审批、交接和编排 | 应用自己的存储、SDK Session 或 Responses 状态 | 控制力强，需要自行做好持久化与运维 |
| Responses API | 直接控制模型调用，自己实现 Agent Loop | 手动维护历史、链式响应或 Conversations | 最灵活，也最容易遗漏超时、重试和恢复 |
| 工作流/脚本 | 步骤确定、可重复的内容构建与发布 | Git、构建产物和 CI 状态 | 可预测；不应为了“智能”引入不必要的自主循环 |

经验法则：能用确定性工作流解决的步骤就固定下来，把 Agent 的自由度限制在研究、决策和异常处理等确有不确定性的环节。

## 长任务的状态机

不要把长任务实现成一个永不结束的对话。应把每个任务保存为可重放的状态机：

```text
queued → running → waiting_for_input
             │          │
             ├→ retrying ┘
             ├→ paused
             ├→ completed
             └→ failed → resumable
```

建议的任务记录至少包含：`task_id`、用户目标、版本化计划、当前步骤、输入/输出引用、工具调用摘要、重试次数、预算、审批记录、错误原因、最后心跳和幂等键。

### 长任务执行清单

1. **切分**：把目标拆成有输入、产出和验收条件的步骤，给每步设置超时和最大重试次数。
2. **检查点**：在外部副作用前后写入 checkpoint；恢复时从最近的已确认检查点继续。
3. **幂等**：工具调用携带幂等键，重复恢复不会重复发文、扣费或修改数据。
4. **暂停点**：需要用户确认、权限或缺少信息时主动进入 `waiting_for_input`，不要循环猜测。
5. **预算**：同时限制步数、Token、时间、工具费用和并发数。
6. **证据**：每一步记录输入摘要、工具参数、结果引用和验证结论，便于重放和审计。

## 长记忆不是“把所有历史塞回 Prompt”

记忆系统应分层，并且每层有明确的写入与淘汰规则：

| 层 | 生命周期 | 存什么 | 检索方式 |
| --- | --- | --- | --- |
| 工作上下文 | 当前回合 | 当前目标、约束、最近观察 | 直接注入，严格限长 |
| 任务记忆 | 单个任务 | 计划、检查点、失败与决策 | `task_id` 精确读取 |
| 情景记忆 | 多次任务 | “何时做过什么、结果如何” | 时间+关键词/向量混合 |
| 语义记忆 | 长期 | 稳定事实、偏好、规则和文档知识 | 权限过滤后的混合检索 |
| 证据存储 | 按需长期 | 原文、版本、引用、工具输出 | 文档 ID、哈希和来源链 |

### 记忆写入策略

- 只写入可复用、可验证且对未来决策有帮助的信息；原始对话不等于长期记忆。
- 为记忆附带来源、时间、作用域、置信度、过期时间和删除策略。
- 先做精确检索，再做关键词/向量检索，最后让模型判断是否真的相关。
- 将“用户偏好”“项目事实”“临时结论”“未经验证猜测”分开，禁止把猜测升级为事实。
- 对敏感数据做最小化存储、脱敏和租户隔离，并提供用户可见的删除入口。

## 上下文压缩与恢复

上下文窗口扩大不能替代上下文工程。每次调用前可按以下顺序组装上下文：

```text
任务目标与硬约束
  + 当前步骤与验收条件
  + 最近工具观察
  + 相关长期记忆（带来源）
  + 压缩摘要与未决问题
  + 本轮可用工具/权限
```

当接近预算时，生成结构化摘要而不是简单截断：保留未完成事项、已验证事实、决策理由、失败尝试、引用和下一步。摘要要版本化，必要时允许从原始事件重新生成，避免错误摘要永久污染记忆。

## 工具、审批与安全边界

工具 schema 是 Agent 的 API 合同：参数要有类型、范围、权限和副作用说明。读操作与写操作分离；发送消息、发布文档、删除数据、支付或改权限等动作默认进入人工审批。

- 为工具设置租户、用户和任务级权限。
- 对外部输入做提示词注入、越权和数据外传检查。
- 沙箱执行代码和文件操作，限制网络、文件系统和资源额度。
- 将工具结果视为不可信观察，不能让工具返回的文本改写系统规则。
- 失败时优先返回可恢复错误；不可恢复错误要保留完整 trace 和人工处理入口。

## 评估与可观测性

Agent 评估必须同时看结果和过程：任务完成率、引用正确率、工具选择准确率、参数错误率、平均步数、恢复成功率、Token/费用、端到端延迟和安全拦截率。

每次运行至少关联 `trace_id`、`task_id`、提示词/工具版本、模型标识、输入输出摘要、检索文档 ID、工具调用、审批和最终验收。把线上失败样例沉淀为离线回归集，变更只有在质量、成本和安全门槛都通过时才发布。

## 生成文档并发布：本项目的落地链路

本知识库采用“研究与正文分离”的发布策略：

1. 采集脚本把候选资料写入 `data/resources.json`，不直接改写正文。
2. 人工核验来源、版本、许可和事实，把结论整理到 `docs/` 对应专题页。
3. `python scripts/audit_docs.py` 检查缺页、标题、资源区块和本地链接。
4. `npm run build` 验证 VitePress 产物。
5. `npm run publish -- -m "docs: update agent architecture"` 执行体检、构建、提交并推送；GitHub Actions 再发布到 Pages。

对长任务 Agent，建议把每次生成结果保存为带元数据的草稿：来源清单、知识截止日期、模型/提示词版本、人工审核状态和发布 commit。只有审核通过的草稿才能进入 `docs/`，这样可以恢复、比较和撤销一次内容生成。

## 一个可执行的最小实现

```python
while task.status not in {"completed", "failed"}:
    state = store.load_checkpoint(task.id)
    context = assemble_context(state, memory, budget=task.context_budget)
    decision = agent.run(context, tools=allowed_tools(state))
    if decision.needs_approval:
        store.pause(task.id, reason="approval")
        break
    result = execute_idempotently(decision.tool_call)
    store.append_event(task.id, decision, result)
    state = reduce_state(state, result)
    store.save_checkpoint(task.id, state)
    if should_compact(state):
        memory.save(summary=compact(state), source=task.id)
```

这段伪代码的重点不是某个框架，而是“事件记录 + checkpoint + 幂等工具 + 可暂停 + 可压缩”。框架可以替换，可靠性边界不能省略。

## 常见误区

- 用无限循环掩盖没有任务边界和验收条件。
- 用一个向量库混放所有聊天、事实、权限和工具输出。
- 只保存最终答案，不保存中间步骤和失败证据。
- 让 Agent 直接拥有发布、删除或支付权限，没有审批和回滚。
- 只看模型 benchmark，不在真实任务上评估框架、工具和数据的组合效果。
- 自动采集结果未经核验就发布，导致过时 API、错误价格或不可追溯结论进入正文。
