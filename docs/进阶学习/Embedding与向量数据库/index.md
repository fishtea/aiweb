# Embedding 与向量数据库

Embedding 把文本、图片、代码等对象编码为向量；向量检索根据距离或相似度找出候选。向量数据库在此基础上提供持久化、索引、过滤、更新、复制和运维能力。它们常用于 RAG、语义搜索、推荐、去重和聚类，但不会自动保证检索正确。

## 学习目标

读完本页后，你应该能够：

- 区分稠密、稀疏、多向量和多模态表示。
- 正确选择 cosine、dot product 与 L2，并理解归一化的影响。
- 区分精确检索、ANN 索引和完整向量数据库。
- 设计分块、混合检索、重排序、权限过滤和增量更新流程。
- 用 Recall@k、MRR、nDCG、延迟和成本评估检索系统。

## Embedding 是什么

Embedding 模型学习一个编码函数：

```text
encoder(object) -> vector
```

向量空间中的接近程度只在模型训练目标和目标任务下有意义。两个对象“语义相似”并不是数学距离天然携带的属性。

### 常见表示方式

| 类型 | 表示 | 优势 | 局限 |
|------|------|------|------|
| 稠密向量 | 每个对象一个较短的浮点向量 | 语义召回、实现成熟 | 精确词、编号和罕见实体可能较弱 |
| 稀疏向量 | 高维且大部分为 0 | 保留词项匹配与可解释性 | 同义改写能力有限 |
| 多向量 | 文档由多个 token/片段向量表示 | 细粒度交互，长文档匹配更强 | 存储和计算更高 |
| 多模态向量 | 文本、图像等映射到共享空间 | 跨模态搜索 | 模态差异和数据偏差需单独评估 |

BM25 是经典稀疏关键词检索方法，不是 Embedding 模型；但它常与稠密检索组合。

## 相似度与距离

### 三种常见度量

```text
dot(x, y) = sum(x_i * y_i)
cosine(x, y) = dot(x, y) / (norm(x) * norm(y))
L2(x, y) = sqrt(sum((x_i - y_i)^2))
```

- **点积**同时受方向和长度影响。
- **余弦相似度**只比较方向，范围通常为 `[-1, 1]`。
- **L2 距离**越小越相似。

对单位归一化向量，点积排序与余弦排序相同，L2 排序也与它们单调对应。未归一化时不能假设三者等价。应遵循模型卡推荐的池化、归一化和距离函数。

### 分数不是通用概率

相似度 `0.8` 不表示“有 80% 概率相关”。不同模型、语言、查询和索引参数会产生不同分数分布。阈值必须在业务评估集上确定，并随模型或数据版本重新校准。

## 查询与文档并不总是对称

许多检索模型把短查询与长文档视为不同角色，并要求不同前缀或指令，例如“为此问题检索证据”和“表示待检索段落”。忽略模型要求的 query/document 模板可能显著降低效果。

入库与查询必须一致记录：

- 模型名称与精确版本。
- 分词、最大长度、截断方式和池化方式。
- query/document 前缀或任务指令。
- 输出维度、归一化和距离函数。

更换上述任一项通常需要重算向量并建立新索引，不能把不同版本的向量直接混在同一空间中比较。

## RAG 检索管线

```text
数据接入
  -> 解析与清洗
  -> 分块并保留结构
  -> 生成稠密/稀疏表示
  -> 建立索引
  -> 查询改写与权限约束
  -> 候选召回
  -> 融合、去重与重排序
  -> 上下文组装
  -> 生成带引用的回答
```

### 分块

分块应尽量保持标题、段落、列表、表格和代码边界。固定 token 长度只是起点，还要考虑：

- 答案证据是否被切散。
- 重叠是否造成重复召回和上下文浪费。
- 父子结构能否支持“短块检索、长块返回”。
- 表格行列、页码和来源是否保留。
- 文档更新后 chunk ID 是否稳定。

不存在适合所有数据的 `512 tokens` 最优值。应根据证据长度、模型限制和评估结果选择。

### 元数据

每个 chunk 至少应保留来源 ID、标题层级、版本、更新时间、权限、租户和可定位片段。引用只写文件名往往不够，最好能定位页码、段落或稳定锚点。

## 精确检索与 ANN

### 精确检索

Flat/brute-force 检索比较所有候选，结果精确、实现简单，适合小规模数据或作为 ANN 召回率的评估基线。规模增长后，其计算成本会线性上升。

### 常见 ANN 索引

| 索引 | 核心思路 | 主要权衡 |
|------|----------|----------|
| HNSW | 多层近邻图搜索 | 高召回和低延迟，但内存、构建和更新成本较高 |
| IVF | 先找聚类分区，再扫描部分分区 | 通过探测分区数量权衡召回和速度 |
| PQ/SQ | 压缩向量或分量 | 降低内存与带宽，可能损失召回 |
| DiskANN 类 | 图索引结合 SSD | 降低内存压力，依赖磁盘与实现优化 |

HNSW 很常见，但不是所有数据库、规模和硬件下的“绝对默认”。其实际查询复杂度、召回和延迟依赖数据分布、图参数和实现，不能笼统承诺严格的对数复杂度。

调参时至少记录：

- HNSW 的 `M`、构建参数和查询 `ef`。
- IVF 的聚类数与 `nprobe`。
- 压缩位数、重排序候选数和内存占用。
- 相对于精确检索的 Recall@k。

## 向量索引与向量数据库

| 能力 | Faiss 等索引库 | 完整向量数据库/数据库扩展 |
|------|----------------|---------------------------|
| 最近邻索引 | 核心能力 | 核心能力 |
| 持久化与恢复 | 需要应用自行设计或使用库支持 | 通常提供更完整机制 |
| 元数据与过滤 | 常在外部系统维护 | 通常原生或紧密集成 |
| 增删改 | 取决于索引类型；并非都要全量重建 | 通常提供 CRUD，但索引维护成本仍存在 |
| 复制、高可用、租户 | 应用负责 | 视产品和部署模式而定 |
| 事务与关系查询 | 不是主要目标 | 数据库扩展可能继承原数据库能力 |

“Faiss 不能删除或增量添加，任何修改都要全量重建”是不准确的。Faiss 的部分索引支持 `add` 和 `remove_ids`，但更新能力、ID 管理和性能随索引类型变化。索引库仍不等于带权限、备份和高可用的数据库。

## 元数据过滤与权限

过滤可以发生在 ANN 搜索前、搜索中或搜索后：

- **预过滤**减少候选，但可能使索引搜索空间过小或执行计划变复杂。
- **后过滤**实现简单，但可能在 top-k 中留下不足数量的合法结果。
- **迭代过滤**在召回不足时继续扩大候选，代价是延迟不稳定。

权限必须在检索层强制执行，不能只在提示词中告诉模型“不要展示无权内容”。多租户系统还需防止缓存、日志和向量 ID 侧漏。

## 混合检索与重排序

### 为什么组合稀疏与稠密检索

- 稀疏检索擅长产品编号、人名、错误码和精确短语。
- 稠密检索擅长同义改写和概念相关性。
- 两者的失败模式不同，组合后通常更稳健，但不是每个任务都必然提升。

结果融合可以使用加权分数或 Reciprocal Rank Fusion（RRF）。来自不同检索器的原始分数尺度通常不可直接相加，使用加权分数前要归一化或校准。

### 重排序

Cross-encoder 或生成式 reranker 会同时读取查询和候选，通常比单向量相似度更精细，但增加延迟与成本。只有当正确证据已经进入候选集时，重排序才有机会把它提到前面；如果 Recall@50 很低，应先修复召回。

## 评估

### 离线检索指标

| 指标 | 回答的问题 |
|------|------------|
| Recall@k | 前 k 个结果是否包含相关证据 |
| Precision@k | 前 k 个结果中有多少相关 |
| MRR | 第一个相关结果排得多靠前 |
| nDCG@k | 多级相关性下，排序质量如何 |
| Success/Hit@k | 每个查询是否至少命中一个相关结果 |

评估集应包含真实查询、同义改写、精确标识符、无答案问题、权限边界和时间敏感问题。标签要明确是“相关文档”“支持答案的证据”还是“最终可回答”，三者不完全相同。

### 端到端指标

还要评估答案正确性、引用支持度、拒答、权限、安全、延迟和成本。检索分数提升不一定带来最终答案提升，过多上下文还可能降低生成质量。

### 性能指标

- 查询 p50/p95/p99 延迟与吞吐。
- 索引构建时间、写入延迟和数据新鲜度。
- 内存、磁盘、网络与副本成本。
- 过滤选择性、并发和故障恢复。
- 在相同硬件和召回目标下比较系统，而不是只比较单次最快值。

## 模型与数据库选型

### Embedding 模型

先用公开基准筛选，再用业务数据决策。MTEB 覆盖检索、分类、聚类、语义相似度等多类任务，并包含多语言扩展；把它描述为“只测试单语言文本检索”是错误的。任何供应商自建 benchmark 都应检查数据、负样本、指标、模型版本和可复现代码。

重点比较：

- 目标语言、领域与文本长度。
- 查询和文档是否不对称。
- 维度、吞吐、批处理和最大输入长度。
- 许可证、隐私、数据驻留和版本稳定性。
- 降维或量化后的目标任务结果。

不要根据一次厂商测试宣布某模型“跨模态、跨语言和长文档全部第一”。模型和 API 会更新，榜单也可能使用不代表业务的合成数据。

### 存储方案

| 条件 | 可优先评估 |
|------|------------|
| 数据量小、离线原型 | Flat/Faiss、SQLite 生态或嵌入式方案 |
| 已有 PostgreSQL 且规模可控 | pgvector，减少系统数量并利用事务与 SQL |
| 独立检索服务和复杂过滤 | Qdrant、Weaviate、Milvus 等，按实测选择 |
| 已有全文搜索平台 | Elasticsearch/OpenSearch 的混合搜索能力 |
| 全托管和弹性优先 | 托管向量服务，重点审核成本、导出和供应商锁定 |

“多少向量必须用哪个产品”没有固定阈值。向量维度、过滤选择性、写入率、召回目标、并发、硬件和运维能力都会改变结论。

## 容量与生命周期

未压缩 FP32 向量的原始存储可粗略估算为：

```text
bytes = vector_count * dimension * 4
```

这不含图索引、ID、元数据、副本、日志和数据库开销。HNSW 图边、多个副本和高维元数据可能显著增加实际占用。

生产系统还要设计：

- 幂等写入和稳定文档/chunk ID。
- 新旧 Embedding 版本双写、回填与切换。
- 删除、过期、撤回和隐私请求的传播。
- 索引快照、备份、恢复与重建时间。
- 文档、向量、索引和生成答案的版本追踪。

## 常见误区

- **向量维度越高检索越准**：维度只是成本与表示能力的一部分，必须实测。
- **相似度阈值可跨模型复用**：不同模型和归一化方式的分数不可直接比较。
- **ANN 结果就是精确最近邻**：ANN 有可调召回误差，应与 Flat 基线对比。
- **换更大模型能解决所有问题**：解析、分块、标签、权限和查询分布常是主要瓶颈。
- **向量数据库就是长期记忆**：记忆还需要写入规则、来源、过期、冲突和删除策略。
- **混合检索与 reranker 总能达到固定提升**：提升依数据和候选质量而定，不存在通用的 85%/92%/97% 阶梯。
- **自托管没有调用费所以免费**：硬件、运维、扩容、监控和升级都要计入总成本。
