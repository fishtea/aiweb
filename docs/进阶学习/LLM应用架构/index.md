# LLM 应用架构

LLM 应用是一个包含交互、编排、知识、模型、安全、评估和运维的系统，不是把请求转发给模型的单一函数。

## 分层架构

| 层 | 责任 |
| --- | --- |
| 交互 | Web、API、流式输出、会话和错误呈现 |
| 编排 | Prompt、状态、工具、RAG、Agent 或工作流 |
| 知识 | 解析、索引、权限、引用和更新 |
| 模型 | 路由、重试、限流、缓存、成本和降级 |
| 安全 | 身份、权限、注入防护、脱敏和审批 |
| 评估 | 离线集、线上反馈、回归和质量门禁 |
| 运维 | 日志、trace、指标、告警、灰度和回滚 |

## 先确定系统类型

- 固定输入输出：Prompt + 结构化输出。
- 私有知识问答：RAG + 权限过滤 + 引用。
- 外部动作：函数调用/MCP + schema + 审批 + 幂等。
- 路径不确定：Agent + 状态机 + 预算 + 可恢复执行。
- 训练或风格适配：先验证数据和评估，再考虑微调。

## 生产闭环

```text
目标与验收 → 最小链路 → 真实评估集 → trace/反馈
    → 失败归因 → 改 Prompt/检索/工具/模型/数据 → 灰度发布
```

## 关键工程约束

1. Prompt、模型、工具、检索和安全配置全部版本化。
2. 任何写操作都有权限、幂等键、审批和回滚路径。
3. 外部输入、检索结果和工具返回值不可信，不能覆盖系统规则。
4. 记录输入摘要、模型 ID、检索文档、工具调用、耗时、Token 和错误。
5. 对上下文、步数、时间、费用和并发设置明确预算。

## 选型原则

先用最简单能通过验收的方案。能用确定性工作流解决的任务不要升级为 Agent；能用检索补充时效知识就不要先微调；能用小模型完成的预处理不要全部交给昂贵模型。
