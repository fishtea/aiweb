# 模型评估与基准

评估的目的不是寻找一个漂亮分数，而是判断模型或系统是否满足目标任务、风险和成本约束，并能在版本变化后发现回归。

## 评估层次

| 层次 | 问题 | 例子 |
| --- | --- | --- |
| 能力 | 模型能否完成任务 | 正确率、代码测试、摘要质量 |
| 系统 | 应用链路是否可靠 | 检索、工具、引用、错误恢复 |
| 生产 | 上线后是否稳定 | 延迟、成本、漂移、人工接管 |
| 安全 | 是否越过风险边界 | 注入、越权、泄露、有害输出 |

## 评估集设计

1. 从真实请求抽样并脱敏，覆盖常见、边界和高风险案例。
2. 保存输入、期望输出、评分标准、来源和数据版本。
3. 按任务类型、难度、语言、长度和失败原因分层。
4. 保留固定回归集，新增线上失败样例前先人工确认。

## 指标选择

不要把一个总分当成质量。按任务组合自动指标、规则检查、程序执行和人工评审；同时记录成本、延迟和安全拦截。LLM-as-a-judge 需要校准、盲测和人工抽查。

## Agent 评估

除最终任务成功率，还要记录计划可行性、工具选择和参数准确率、步数、循环、重试恢复率、证据/引用覆盖率、人工接管率和副作用错误率。

## 发布门禁

```text
基线 → 候选版本 → 固定集对比 → 失败归因
  → 质量/成本/安全门槛 → 灰度 → 线上回归集
```

任何模型、Prompt、工具、检索或安全配置变更都应有版本、对照结果和回滚方案。

## 常见误区

- 只测 benchmark，不测自己的真实任务。
- 只看平均分，不看长尾和高风险样例。
- 测试集被反复调参，导致数据泄漏。
- 只评估最终答案，不保存中间工具轨迹和证据。
